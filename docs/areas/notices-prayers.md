# Notices, notice alerts, prayers, All cars

The old push feature was removed 2026-07-11 (archived to `../Archive/push-notifications-2026-07-11/`). Its `push_subscriptions`/`notifications`/`notification_recipients` tables may still exist in prod; **never reuse those names** (`create table if not exists` would silently keep the old shape). Notice alerts (2026-10-15) are a fresh port from MyYouthCamp: see below.
- **Notices (R6; migration 0028, `supabase.notices.ts`).** Flag `modules.notices` `off|on`, default **off** (admin turns it on in Settings). Admin/oversight compose + send to any subset of the 4 quad accounts (perm `notice:write`; quad logins only read their own); More > Notices (30-day history; admin/oversight see recipients); Home card for 24 h after send, not dismissable; sender can delete. No priority, push, schedule, edit or read receipts. `/notices` is in `vercel.json` and `sw.js` `API_RE`.
- **Notice alerts (web push; migration 0029 `notice_push_subscriptions`, id = sha256(endpoint) prefix, SW `ysc-v110`).** Only while `modules.notices` is on. More > Notices card: Turn on alerts (the ONLY place permission is asked; `Notification.requestPermission` runs synchronously in the tap) / Turn off alerts; states on / off / blocked by browser / not supported / iPhone not on Home Screen ("Add to Home Screen first") / not set up (VAPID env unset). Routes `GET /notices/push` (`{publicKey|null}`), `POST /notices/push` (subscribe), `POST /notices/push/off`; perm `notice:alerts` = admin, oversight, quad. Sending: after the notice insert, to active quad logins it is addressed to plus every subscribed active admin/oversight (`receivesNoticePush`); payload `{title:'New notice', body:<notice title, ~120 chars>, screen:'notices'}` only; 404/410 deletes the row; any other failure logs `PUSH_FAILED` (code only) and never fails the send. Click opens More > Notices (`push-nav` message, or cold start `/?nav=notices`). Env: `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`. Tests: `notice-push.service.test.ts`, `notice-push.spa.test.ts`.
- **Leader alerts, Part F (migration 0056, SW `ysc-v173` when Part F shipped (Part L makes it `ysc-v174`), 2026-11-07, branch `feat/bday-alerts`).** A push subscription now also carries the device's "I am" leader and two phone prefs: `notice_push_subscriptions.leader_id` (fk leaders, on delete set null), `bday_on`, `lgrem_on` (default true). The SPA re-posts `POST /notices/push` with `{endpoint, keys, leaderId, prefs?}` (`_pushLeaderSync`, from `setMyLeaderId`, `_ntPushFinish`, and once after boot; `yap_push_leader` remembers what the server holds (the subscribe reply's `leaderId`, the saved value: null for an unknown or inactive leader, so the next boot or pick posts again); every re-post carries `leaderId` because a missing one saves null). An unknown or inactive leader saves null; a missing `prefs` key keeps the stored value. `GET /notices/push?endpoint=` returns `{publicKey, modules:{birthdayAlerts,lifegroupReminders}, leaderId?, prefs?}` (leader and prefs only when that row belongs to the caller). A different login on a subscribed phone (`_iamNewLogin`) re-posts with leader null; a 403 (no `notice:alerts`) drops the browser subscription (A1).
  - **Modules** `modules.birthdayAlerts` (requires `notices`) and `modules.lifegroupReminders` (requires `notices`, `lifegroupReport`), each `off|on`, default off. In `MODULE_TREE` birthdayAlerts sits right after notices and lifegroupReminders after lifegroupReport (resolveModules is one pass in tree order, so a requirement must come earlier). `alertModuleOn(modules, key)` (admin counts as on). Settings shows both switches under Notices, greyed with "Needs Notices. Turn Notices on first." / "Needs Lifegroup report. Turn Lifegroup report on first (Elvanto for this location below).". A save turns an alert switch off with its parent (`_setupPatch`), so turning Notices or Lifegroup report off is never refused by `moduleProblems`. Fixtures `module-tree.json` (16 entries), `module-owners.json`, `baseline-nav.json`.
  - **Phone switches** in the Alerts card (`#nt-pref-bday` Birthdays, `#nt-pref-lgrem` Lifegroup reminders, `_ntPrefSet`): shown only while alerts are on for the phone and that module is on; with no "I am" picked, one line "Pick 'I am' to get birthday and lifegroup alerts." replaces them. Copy is `_ntAlertsCopy(modules)`.
  - **Payload and deep links:** `{title, body, tag, screen, ...params}`; `tag` = `notice` / `bday` / `lgrem:<groupId>` (kinds never replace each other); missing tag or screen = notices (old payloads). A click posts `push-nav` or opens `/?nav=<screen>&...`. One SPA router, `_navRoute`, validates every param (`ids` 1-10 uuids, `date` YYYY-MM-DD, any other key a uuid), clears `?nav=` first; unknown or invalid = notices. A cold start now runs it after the first render.
  - **Server:** `src/services/push-send.ts` (`sendToSubs`, `readVapid`, `webPushSender`; TTL 3600; 404/410 prunes the row; `notice.service` uses it too). `alert_sends` (`kind, key, leader_id`, unique; `IAlertSendRepository.claim` = insert on conflict do nothing, so a repeat is a no-op; `prune` drops rows over 30 days). `alert-run.service.ts` `makeAlertRun(deps, kinds).run(now, which)` returns `{bday?: Counts}` with `Counts = {leaders, sent, failed, skipped: 'window'|'push-off'|'module-off'|'stale'|null}`; VAPID unset = `push-off` and Notices off = `module-off` for every kind, nothing claimed; eligible subs = leader set and active, user active with `notice:alerts`; it stops claiming after `ALERT_BUDGET_MS` (40 s per run, shared by the kinds); failures log once as `ALERT_PUSH_FAILED`. `container.ts` registers `bday` and, on branch `feat/lg-reminders` only, `lgrem` (Part L, below): **on master today only `bday` runs, so `lifegroupReminders` does nothing until that branch ships.** `AlertCtx` also carries `structure` (the run passes `cfg.structure`) because the lifegroup kind needs `groupVisible`.
  - **Triggers:** `POST /sync/alerts` (link token; the console calls it every 15 minutes on the quarter hour; runs every kind; not gated on `liveLink`) and `GET /sync/alerts` (`CRON_SECRET`; runs `bday` only). **No `vercel.json` cron entry was added** (`CRON_SECRET` is not set), so the console trigger is the only scheduler today. See `docs/areas/env-prod-db.md`.
  - Tests: `alert-run.test.ts`, `alerts.spa.test.ts`, `notice-push.service.test.ts` ("subscription carries leader and prefs", pushConfig modules), `module-tree.test.ts`, `express-adapter.sync.test.ts` (F4 block), `schema-version.test.ts`.
- **Birthday alerts, Part B (`birthday-alert.ts`, `LINK_REV` 23, 2026-11-07).** `makeBirthdayKind({connections, students, dnc})` = the `bday` kind, registered in `container.ts`. Skipped as `module-off` unless `modules.birthdayAlerts` resolves on (`alertModuleOn`); `day` = `brisbaneToday(now, tz)` (site time zone); sends only from 08:00 to 11:59 site time, else `skipped: 'window'` (a missed morning is skipped). Subs filtered by `bdayOn`; students from `students.findAll()` (graduated omitted), "connected" = a row in `connections` and nothing else, DNC students out (`Dnc.ids()`), `isRealDob` filter. One alert per leader per day listing their students turning today (claim key = the day; each of the leader's devices gets it). `birthdayToday(dob, day)` returns the age or null (Feb 29 shows on 28 Feb in non-leap years; born today = null). Payload `{title:'Birthday', body, tag:'bday', screen:'student', ids}` (ids <= 10, students sorted by first name then id). Body: `🎂 Sam turns 16 today` / `🎂 Sam turns 16 and Mia turns 15 today` / `🎂 Sam (16), Mia (15) and Leo (14) have birthdays today`; over 120 characters it becomes `🎂 A (n), B (n), … and N more today`. Tap: `_navRoute` `student` calls `_bdayList(ids)`, which keeps only the ids in this login's `GET /students`; one opens `showStudentDetail`, several open a "Birthdays today" modal with a button per student, none shows "Today's birthdays aren't on this login." The shared-login leak (anyone can pick any leader) is the accepted risk S7. DOBs arrive by the roster push (see `docs/areas/link-contract-revs.md`, `LINK_REV` 23) and the CSV import. Tests: `birthday-alert.test.ts` (30), `alerts.spa.test.ts` (student link), plus the `dobFixes` tests.
- **Lifegroup report reminders, Part L (`lifegroup-reminder.ts`, built 2026-11-07 on `feat/lg-reminders`, shipped with `feat/lg-fast` 2026-11-18, SW `ysc-v178`). Live in code; `modules.lifegroupReminders` stays Off until the admin turns it on (Youth Setup > Modules), and a phone also needs "I am" and the Lifegroup reminders switch.** **18 Nov: a second push at 08:00 to 08:59 (site time) the morning after the meeting if the week's report is still not in (`nudgeOccurrences`, own claim key `<groupId>:<D>:n2`, body "<group>: still no report from last night. Tap to fill it in."); the console's 15-minute alerts trigger (`sync.controller` `alerts`) covers both windows. Any leader's report (even a pending one) stops both pushes for every leader. The tap opens that group's form for the meeting week `d`.** `makeLifegroupKind({link})` (the leaders come from `AlertCtx.leaders`, the run's one read) = the `lgrem` kind (also the `alert_sends` kind), registered in `container.ts`. 2 hours after a lifegroup meets (site time), each Elvanto leader of that group whose "I am" device has `lgremOn` gets one push, unless that week's report is already in. No network call: it reads the groups mirror (`link.groups()`), the roster, the leaders and the outbox.
  - **Skips:** `module-off` unless `alertModuleOn(lifegroupReminders)` (resolution also turns it off when `lifegroupReport` or `liveLink` is off; admin counts as on); no sub with `lgremOn` = returns early; groups mirror `takenAt` missing or older than 6 h = `stale`.
  - **When:** `meetsTime(meets)` (`link-rules.ts`) reads the first `h:mm AM|PM` (also `a.m.`/`p.m.`) as minutes after midnight, else null; a group with no weekday or no time is never reminded. `dueOccurrences(meets, now, tz)`: D = today or yesterday (site-local) on the meets weekday; due = D at the meets time + 120 min; sent while `due <= now < due + 60 min` (a Saturday 10:30 PM group is still reminded after midnight). Item key `<groupId>:<D>`, so each D is sent once per leader.
  - **Done (`reportDone(g, outbox, D, today)`):** `'unreadable'` first when `thisWeek` is unreadable (the group is skipped whatever D is). Otherwise done when, for D's Mon-Sun week, any of: a `submitReport`/`editReport` outbox row for the group with status pending, claimed, sent or unclear and `payload.date` in that week; a mirror `lastReport`/`history` entry in that week; `thisWeek` is reported or did-not-meet and D is in the current week. The outbox read is `listActions` for both types and those 4 statuses, `serviceDateFrom: today - 8`.
  - **Who:** leader members of the group go through the inverted `rosterPersonMatcher` (active leaders only; shared with `link.service`, which now imports it from `link-rules.ts`) to an app leader id. An Elvanto leader with no app leader adds to `unlinked`. A device whose login fails `can('link:use') && modeAllows(lifegroupReport mode) && groupVisible` is not sent to and adds to `hidden` (so `lifegroupReport: 'admin'` reaches the admin device only). `groupVisible` is exported from `link.service.ts` for this.
  - **Payload:** `{title, body, tag:'lgrem:<groupId>', screen:'lgreport', g, d}`; the body shows the group name cut to 40 characters (39 + `…`) and the time as `6:30 PM`. Group name and time only: no member names (A2).
  - **Tap:** `_navRoute` `lgreport` (needs `g` uuid and `d` YYYY-MM-DD) calls `_lgremOpen(g, d)`: opens Lifegroups, loads the groups, toasts "This group isn't on this login." if the group is not there, otherwise opens the group and starts the report form for D unless `_lkWeekReport` already has one for that week or the group has an app-filed report still pending (`openAction`). A dirty edit form is left open as is (an unsaved edit has no draft); only the Lifegroups page is shown. A failed load opens nothing. No SPA copy of `meetsTime` exists (the server decides when to send), so `spa-rules.md` is unchanged.
  - **Tests:** `lifegroup-reminder.test.ts` (27: the due window incl. DST and Brisbane, `reportDone` rules, the sweep: payload, second run sends 0, name cut, stale mirror, unlinked, hidden, `lgremOn` off, module off, admin-only mode), `link-rules.test.ts` (`meetsTime`, `rosterPersonMatcher`), `alerts.spa.test.ts` (`_lgremOpen`, bad `g`/`d`, SW `lgrem` payload), `impeccable-ys.spa.test.ts` (SW pin `ysc-v174`).

### Prayers, Simple logins, All cars

- **Prayers** can be turned off (Youth Setup → Modules; turning it on needs a reload). Prayer text is plaintext at rest (Security notes).
- **Simple logins:** see Roles. **All cars** (Bus): a collapsed read-only section under the My car tab, suburb + name + grade only, `GET /bus/run/cars`, polled only while open.
