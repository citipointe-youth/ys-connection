# Notices, notice alerts, prayers, All cars

The old push feature was removed 2026-07-11 (archived to `../Archive/push-notifications-2026-07-11/`). Its `push_subscriptions`/`notifications`/`notification_recipients` tables may still exist in prod; **never reuse those names** (`create table if not exists` would silently keep the old shape). Notice alerts (2026-10-15) are a fresh port from MyYouthCamp: see below.
- **Notices (R6; migration 0028, `supabase.notices.ts`).** Flag `modules.notices` `off|on`, default **off** (admin turns it on in Settings). Admin/oversight compose + send to any subset of the 4 quad accounts (perm `notice:write`; quad logins only read their own); More > Notices (30-day history; admin/oversight see recipients); Home card for 24 h after send, not dismissable; sender can delete. No priority, push, schedule, edit or read receipts. `/notices` is in `vercel.json` and `sw.js` `API_RE`.
- **Notice alerts (web push; migration 0029 `notice_push_subscriptions`, id = sha256(endpoint) prefix, SW `ysc-v110`).** Only while `modules.notices` is on. More > Notices card: Turn on alerts (the ONLY place permission is asked; `Notification.requestPermission` runs synchronously in the tap) / Turn off alerts; states on / off / blocked by browser / not supported / iPhone not on Home Screen ("Add to Home Screen first") / not set up (VAPID env unset). Routes `GET /notices/push` (`{publicKey|null}`), `POST /notices/push` (subscribe), `POST /notices/push/off`; perm `notice:alerts` = admin, oversight, quad. Sending: after the notice insert, to active quad logins it is addressed to plus every subscribed active admin/oversight (`receivesNoticePush`); payload `{title:'New notice', body:<notice title, ~120 chars>, screen:'notices'}` only; 404/410 deletes the row; any other failure logs `PUSH_FAILED` (code only) and never fails the send. Click opens More > Notices (`push-nav` message, or cold start `/?nav=notices`). Env: `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`. Tests: `notice-push.service.test.ts`, `notice-push.spa.test.ts`.
- **Leader alerts, Part F (migration 0056, SW `ysc-v173`, 2026-11-07, branch `feat/bday-alerts`).** A push subscription now also carries the device's "I am" leader and two phone prefs: `notice_push_subscriptions.leader_id` (fk leaders, on delete set null), `bday_on`, `lgrem_on` (default true). The SPA re-posts `POST /notices/push` with `{endpoint, keys, leaderId, prefs?}` (`_pushLeaderSync`, from `setMyLeaderId`, `_ntPushFinish`, and once after boot; `yap_push_leader` remembers what the server holds; every re-post carries `leaderId` because a missing one saves null). An unknown or inactive leader saves null; a missing `prefs` key keeps the stored value. `GET /notices/push?endpoint=` returns `{publicKey, modules:{birthdayAlerts,lifegroupReminders}, leaderId?, prefs?}` (leader and prefs only when that row belongs to the caller). A different login on a subscribed phone (`_iamNewLogin`) re-posts with leader null; a 403 (no `notice:alerts`) drops the browser subscription (A1).
  - **Modules** `modules.birthdayAlerts` (requires `notices`) and `modules.lifegroupReminders` (requires `notices`, `lifegroupReport`), each `off|on`, default off. In `MODULE_TREE` birthdayAlerts sits right after notices and lifegroupReminders after lifegroupReport (resolveModules is one pass in tree order, so a requirement must come earlier). `alertModuleOn(modules, key)` (admin counts as on). Settings shows both switches under Notices, greyed with "Needs Notices. Turn Notices on first." / "Needs Lifegroups. Turn Lifegroups on first.". Fixtures `module-tree.json` (16 entries), `module-owners.json`, `baseline-nav.json`.
  - **Phone switches** in the Alerts card (`#nt-pref-bday` Birthdays, `#nt-pref-lgrem` Lifegroup reminders, `_ntPrefSet`): shown only while alerts are on for the phone and that module is on; with no "I am" picked, one line "Pick 'I am' to get birthday and lifegroup alerts." replaces them. Copy is `_ntAlertsCopy(modules)`.
  - **Payload and deep links:** `{title, body, tag, screen, ...params}`; `tag` = `notice` / `bday` / `lgrem:<groupId>` (kinds never replace each other); missing tag or screen = notices (old payloads). A click posts `push-nav` or opens `/?nav=<screen>&...`. One SPA router, `_navRoute`, validates every param (`ids` 1-10 uuids, `date` YYYY-MM-DD, any other key a uuid), clears `?nav=` first; unknown or invalid = notices. A cold start now runs it after the first render.
  - **Server:** `src/services/push-send.ts` (`sendToSubs`, `readVapid`, `webPushSender`; TTL 3600; 404/410 prunes the row; `notice.service` uses it too). `alert_sends` (`kind, key, leader_id`, unique; `IAlertSendRepository.claim` = insert on conflict do nothing, so a repeat is a no-op; `prune` drops rows over 30 days). `alert-run.service.ts` `makeAlertRun(deps, kinds).run(now, which)` returns `{bday?: Counts}` with `Counts = {leaders, sent, failed, skipped: 'window'|'push-off'|'module-off'|'stale'|null}`; VAPID unset = `push-off` and Notices off = `module-off` for every kind, nothing claimed; eligible subs = leader set and active, user active with `notice:alerts`; it stops claiming after `ALERT_BUDGET_MS` (40 s per run, shared by the kinds); failures log once as `ALERT_PUSH_FAILED`. Only `bday` is registered in `container.ts`; the lifegroup reminder sweep (Part L) is not built yet, so `lifegroupReminders` does nothing today.
  - **Triggers:** `POST /sync/alerts` (link token; the console calls it every 15 minutes on the quarter hour; runs every kind; not gated on `liveLink`) and `GET /sync/alerts` (`CRON_SECRET`; runs `bday` only). **No `vercel.json` cron entry was added** (`CRON_SECRET` is not set), so the console trigger is the only scheduler today. See `docs/areas/env-prod-db.md`.
  - Tests: `alert-run.test.ts`, `alerts.spa.test.ts`, `notice-push.service.test.ts` ("subscription carries leader and prefs", pushConfig modules), `module-tree.test.ts`, `express-adapter.sync.test.ts` (F4 block), `schema-version.test.ts`.
- **Birthday alerts, Part B (`birthday-alert.ts`, `LINK_REV` 23, 2026-11-07).** `makeBirthdayKind({connections, students, dnc})` = the `bday` kind, registered in `container.ts`. Skipped as `module-off` unless `modules.birthdayAlerts` resolves on (`alertModuleOn`); `day` = `brisbaneToday(now, tz)` (site time zone); sends only from 08:00 to 11:59 site time, else `skipped: 'window'` (a missed morning is skipped). Subs filtered by `bdayOn`; students from `students.findAll()` (graduated omitted), "connected" = a row in `connections` and nothing else, DNC students out (`Dnc.ids()`), `isRealDob` filter. One alert per leader per day listing their students turning today (claim key = the day; each of the leader's devices gets it). `birthdayToday(dob, day)` returns the age or null (Feb 29 shows on 28 Feb in non-leap years; born today = null). Payload `{title:'Birthday', body, tag:'bday', screen:'student', ids}` (ids <= 10, students sorted by first name then id). Body: `🎂 Sam turns 16 today` / `🎂 Sam turns 16 and Mia turns 15 today` / `🎂 Sam (16), Mia (15) and Leo (14) have birthdays today`; over 120 characters it becomes `🎂 A (n), B (n), … and N more today`. Tap: `_navRoute` `student` calls `_bdayList(ids)`, which keeps only the ids in this login's `GET /students`; one opens `showStudentDetail`, several open a "Birthdays today" modal with a button per student, none shows "Today's birthdays aren't on this login." The shared-login leak (anyone can pick any leader) is the accepted risk S7. DOBs arrive by the roster push (see `docs/areas/link-contract-revs.md`, `LINK_REV` 23) and the CSV import. Tests: `birthday-alert.test.ts` (30), `alerts.spa.test.ts` (student link), plus the `dobFixes` tests.

### Prayers, Simple logins, All cars

- **Prayers** can be turned off (Youth Setup → Modules; turning it on needs a reload). Prayer text is plaintext at rest (Security notes).
- **Simple logins:** see Roles. **All cars** (Bus): a collapsed read-only section under the My car tab, suburb + name + grade only, `GET /bus/run/cars`, polled only while open.
