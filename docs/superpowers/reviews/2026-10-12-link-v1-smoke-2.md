# Elvanto link V1 smoke re-run (2026-10-12)

Re-run of the laptop smoke test against `feat/elvanto-link-app` at `3d0e5b8`, after the single `POST/DELETE /link/actions` routes were removed (phone writes now use `POST /link/batch`). No source file was edited. Memory mode only, no real database.

## Setup

- `PERSISTENCE=memory PORT=4320 LINK_SYNC_TOKEN=<throwaway 32 chars> npm run start`, in the background. Port 4310 (unrelated process) was not touched. The token is not recorded here.
- Fixtures: scratch copies of `push-*.json` from `src/tests/fixtures/elvanto-link/` with `takenAt` = now and service 1 dated today (Brisbane). Claim used `claim-request.json` as is.
- Admin login is `POST /auth/login` with `{"email":"admin","password":"demo1234"}` (the field is `email`, not `username`). Shadow was set with `PATCH /settings` `{"ministryConfig":{"modules":{"newYouthForms":"shadow"}}}`.
- Contract details learned: `checkIn` and `firstTimerCheckIn` payloads need `serviceId` as well as `serviceTimeId` (strict schema; without it the item is refused `VALIDATION_ERROR`). `GET /link/checkin` takes `?serviceTime=<serviceTimeId>`, not `serviceTimeId`.

## Observations (not failures)

1. Resending a batch that held a check-out that cancelled a pending check-in does not give `replay` for the check-out item. The check-out never gets its own outbox row, so the resend returned `refused` `BAD_REQUEST` "Not checked in to this service." (the check-in item itself replays, as `status:"cancelled"`). A phone retrying after a lost response would see a refusal for an item that actually took effect.
2. A check-in payload without `serviceId` is refused with a generic `VALIDATION_ERROR` "Validation failed", with no field named.
